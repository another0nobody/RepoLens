# 第 01 章：项目全貌

> 阅读时间：30 分钟
> 前置：第 00 章
> 目标：先建立一张“RepoLens 是怎么工作的”地图

---

## 1.1 一句话

> **RepoLens 输入一个本地仓库或公开 GitHub 仓库，先做确定性扫描，再让 Agent 解读，最后生成一份每项结论都能回到文件/行号的报告。**

它解决的不是“帮我总结这个项目”，而是：

- 这个项目用了哪些技术？
- 每项技术究竟用在哪里？
- 项目的结构是什么？
- 有哪些风险？
- 我该按什么顺序读代码？

而且每个判断要尽量能核对。

---

## 1.2 为什么不直接问 ChatGPT

如果你把一个仓库压缩成几段 README 发给模型，会得到看似合理的回答，但：

```text
模型可能编造文件名
模型可能编造版本号
模型不知道依赖清单里到底有没有某项技术
模型不会告诉你某个 import 在第几行
```

RepoLens 的核心差异是：

```text
扫描器先产生事实
→ Agent 只能基于事实做解释
→ 报告保留证据
→ 用户可以打开证据核对
```

这叫 **evidence-first（证据先行）**。

---

## 1.3 三层架构

```text
┌─────────────────────────────────────────────┐
│ 1. 扫描层 scanner.py                        │
│    文件遍历 / 语言 / 依赖清单 / import      │
│    → 技术候选 / 模块 / 行号 / 证据          │
│    不调用模型，结果确定                     │
└──────────────────────┬──────────────────────┘
                       │ Snapshot（事实）
┌──────────────────────▼──────────────────────┐
│ 2. Agent 层 agent.py / tools.py / pipeline  │
│    模型 + 工具 + 中间件                     │
│    → 解释技术、分层、风险、学习路径          │
│    失败时降级为规则报告                     │
└──────────────────────┬──────────────────────┘
                       │ RepoInsight（AI 结论）
┌──────────────────────▼──────────────────────┐
│ 3. 报告与界面层 report.py / server / Vue    │
│    合并事实 + AI 结论                       │
│    → JSON / SQLite / SSE / 报告页           │
│    → 证据代码 / 风险 / ADR / 追问核对       │
└─────────────────────────────────────────────┘
```

记住这个分工：

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| 扫描层 | 事实 | 不做主观解释 |
| Agent 层 | 解释、归纳、建议 | 不伪造事实 |
| 报告/界面 | 呈现、核对、交互 | 不重新发明扫描结果 |

## 1.4 用户看到的一次完整流程

```text
1. 首页输入 examples/demo_shop
2. 浏览器 POST /api/analyze
3. 后端创建 run，启动后台线程
4. 扫描器扫描目录，得到 Snapshot
5. Agent 看到仓库概览，调用工具核实技术
6. 模型提交 RepoInsight 结构化结果
7. 后端合并 Snapshot + RepoInsight，生成报告
8. 报告保存为 JSON + SQLite 索引
9. 前端通过 SSE 实时看到步骤，通过 /api/report 拿到报告
10. 用户打开技术卡、代码证据、风险面板、追问
```

对应的核心文件：

```text
frontend/src/views/HomeView.vue
repolens/server.py
repolens/pipeline.py
repolens/agent.py
repolens/tools.py
repolens/scanner.py
repolens/report.py
frontend/src/views/ReportView.vue
```

第 03 章会把这条链路逐段拆开。

## 1.5 项目的五个核心设计

### 1. 事实与解释分离

- `Snapshot` 是扫描器产出的事实；
- `RepoInsight` 是模型产出的解释；
- `report.build_report()` 把两者合并，并明确标记 AI 推断。

### 2. 证据可追溯

每项技术尽量带：

```text
modules: 哪个文件、哪一行、导入了什么
evidence: 依赖清单/代码/配置中的原文
confidence: 高/中/低
```

前端点击证据可以打开只读代码查看器。

### 3. AI 可以失败，产品不能白屏

- 没有 API Key：生成规则报告；
- 模型超时/报错：降级扫描；
- 克隆需要审批：用户拒绝就结束；
- SSE 断线：前端可重连，SQLite 保存事件。

### 4. 本地优先

- 默认只监听 `127.0.0.1`；
- 扫描只读；
- 不把整仓上传给模型；
- 工具返回片段，且脱敏；
- `.env`、私钥、敏感文件拒绝读取。

### 5. 可解释的界面

报告页不是“一个大模型总结”，而是：

```text
先看什么 → 技术栈 → 模块地图 → 架构 → 学习 → 追问
```

以及：

```text
风险面板 / 依赖图 / 分析过程
```

## 1.6 当前报告页的层级

默认 5 个核心 Tab：

```text
技术栈 / 模块地图 / 架构解读 / 学习路线 / 追问
```

其他视角收进「更多视图」：

```text
依赖图 / 风险面板 / 分析过程
```

报告头：

```text
重新分析    更多 ▾
```

「更多」里有：

```text
对比历史 / 复制链接 / 导出 Markdown / 导出 JSON
```

首屏统计压缩为 4 格：

```text
文件 / 代码行数 / 技术项 / 风险提示
```

这是为了降低初学者的选择成本，不是删除功能。

## 1.7 demo_shop 是什么

仓库自带一个很小的演示项目：

```text
examples/demo_shop/
├── backend/       FastAPI + SQLAlchemy + Redis
├── frontend/      React + TypeScript + Vite
├── Dockerfile
├── docker-compose.yml
└── .github/workflows/ci.yml
```

它故意包含多种技术，用来演示：

- Python / TypeScript 两种语言；
- 前后端分离；
- PostgreSQL / Redis；
- Docker Compose；
- GitHub Actions；
- 多个入口文件；
- 模块依赖图。

第 02 章会用它跑第一遍。

## 1.8 RepoLens 不做什么

- 不是完整安全审计；
- 不联网查 CVE；
- 不保证 AI 的每句话都正确；
- 不替代阅读源码；
- 不自动修改仓库；
- 不上传整个仓库；
- 不做持续后台监控（当前没有 Watch 模式）。

它做的是：

> 帮你更快建立仓库地图，并把“为什么这么说”保留下来。

---

## 1.9 你应该记住的三个词

### Snapshot

扫描器的全部结果。
包含文件、语言、清单、技术、模块、入口、依赖图。

### RepoInsight

模型的结构化结论。
包含技术解释、架构、风险、学习路径等。

### Evidence

证据。
通常是 `path:line` + 一段原文。
报告和追问都尽量引用它。
