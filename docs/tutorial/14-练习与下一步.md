# 第 14 章：练习与下一步

> 阅读时间：2–6 小时（按练习量）  
> 前置：前面章节  
> 目标：从“看懂”走到“改得动”

---

## 14.1 练习原则

按难度递进：

```text
先只读
→ 再改词典/文案
→ 再改扫描器
→ 再改报告/API
→ 最后改前端/评测
```

每次只改一件事，并跑验证：

```powershell
..\.venv\Scripts\python.exe -m unittest discover -s tests -v
..\.venv\Scripts\python.exe scripts\evaluate.py
cd frontend
npm run build
```

---

## 14.2 Level 0：只读观察

### 练习 0.1 追一条报告

1. 用 `demo_shop` 生成报告；
2. 打开 `data/reports/<run_id>.json`；
3. 找到 `techs` 里的 Redis；
4. 找到它的 `modules`、`evidence`、`confidence`；
5. 回到页面，打开技术详情，确认显示一致。

**验收**：能指出报告 JSON 与页面卡片的对应关系。

### 练习 0.2 无 Key 报告

用无 Key 环境运行一次，找出：

- 哪些字段来自规则；
- 哪些字段为空；
- 页面如何提示。

**验收**：能解释“降级”不是“报错”。

## 14.3 Level 1：改词典

### 练习 1.1 增加一项技术

文件：`repolens/catalog.py`

选一个你熟悉的库/工具，增加：

```python
T("Meilisearch", "数据库", ("meilisearch",), "轻量全文搜索", "any")
```

要求：

- 分类必须在 `CATEGORIES`；
- aliases 至少一个常见包名；
- 不与其他条目冲突。

**验收**：

```text
扫描包含该依赖的仓库时，技术栈出现它
证据指向清单/import
```

### 练习 1.2 修正一项技术描述

找一个 `hint` 不够准确的条目，改成更清楚的一句话。  
注意不要写营销文案。

**验收**：技术详情/卡片兜底文案更准确。

## 14.4 Level 2：改扫描器

### 练习 2.1 增加入口文件名

文件：`repolens/scanner.py` 的 `_find_entry_points()`。

例如当前已支持：

```text
server.js / server.ts / app.ts / main.tsx
```

再增加一个你熟悉的入口：

```text
worker.js
```

要求：

- 只影响入口识别；
- 不误伤依赖清单；
- 跑评测。

**验收**：fixture 中对应文件出现在 `entry_points`。

### 练习 2.2 增加一个语言后缀

文件：`LANGUAGE_BY_SUFFIX`。

例如增加：

```text
.fs → F#（is_code=True）
```

**验收**：

- 文件被统计；
- 语言出现在报告；
- 不误判二进制。

### 练习 2.3 增加一个忽略目录

例如：

```text
.venv312
```

思考：

- 是否会影响现有仓库？
- 是否应该支持通配？
- 是否要测试？

## 14.5 Level 3：改报告/规则

### 练习 3.1 增加风险规则

文件：`repolens/risk.py`。

增加一条规则，例如：

```text
没有 README → 低风险
```

要求：

- 有 title/detail/action；
- 不与已有 finding 重复；
- 有测试。

**验收**：风险面板出现该 finding，计数正确。

### 练习 3.2 增加统计字段

文件：`report.build_report()`。

增加：

```json
"stats": {
  "test_file_count": 3
}
```

要求：

- 旧报告 normalize 不崩；
- 前端可选显示；
- 测试覆盖。

## 14.6 Level 4：改前端

### 练习 4.1 增加一个空状态

选一个 Tab（例如依赖图），当没有数据时显示：

```text
这个仓库没有可解析的本地 import。
```

要求：

- 不只显示空白；
- 给出下一步建议；
- 移动端不溢出。

### 练习 4.2 改技术卡信息

尝试：

- 增加“用途标签”；
- 或把“版本未知”改成更友好的文案。

要求：

- 不破坏卡片高度；
- 21 项技术仍然可扫读；
- 详情抽屉信息不丢。

### 练习 4.3 增加一个可访问性细节

例如：

- 给某个图标按钮加 `aria-label`；
- 给空状态加 `role="status"`；
- 检查键盘 Tab 顺序。

**验收**：只用键盘可以完成主要操作。

## 14.7 Level 5：测试/评测

### 练习 5.1 给风险规则加测试

文件：`tests/test_risk_unit.py`。

覆盖：

- 有 README；
- 无 README；
- 无 README 但已有相同风险（去重）。

### 练习 5.2 增加评测 fixture

文件：

```text
evals/fixtures/my_fixture/

```

要求：

- 至少 3 个文件；
- 至少 1 个技术；
- 至少 1 个入口；
- expected 来自真实扫描，不是猜。

**验收**：

```powershell
..\.venv\Scripts\python.exe scripts\evaluate.py --case my_fixture
```

通过。

## 14.8 Capstone：分析一个你自己的仓库

选一个你写过的项目（不要用公司的私有代码上传）。

完成：

1. 用 RepoLens 生成报告；
2. 读“先看什么”，按路线读 30 分钟；
3. 打开风险面板，挑 3 条能验证的风险；
4. 为一项核心技术生成 ADR；
5. 追问 3 个问题：
   - 最核心的模块是什么？
   - 哪个文件最值得先读？
   - 有哪些测试空白？
6. 检查回答的引用核对；
7. 写一份 500 字“这个项目下一步最该改什么”。

**验收**：

- 至少一条风险有证据；
- 至少一条回答引用可核对；
- ADR 不编造动机。

## 14.9 Capstone 2：做一个迷你 Agent

把 RepoLens 简化成 200 行以内：

```text
输入一个目录
→ 扫描文件/依赖
→ 模型总结
→ 输出 JSON
```

要求：

- 事实与模型输出分开；
- 模型失败有降级；
- 有至少 2 个测试；
- 不读敏感文件。

这是理解本项目架构的最好方式。
